# 3차 고도화 구현 계획: 특권 권한 관리 (PAM) 및 시스템 게이트웨이화

## 1. 개요
PTSS의 최종 단계는 단순한 접속 도구를 넘어, 기업 내 모든 인프라 접근을 통제하고 감시하는 **PAM(Privileged Access Management)** 게이트웨이가 되는 것입니다. 이번 단계에서는 실시간 통제 강화와 감사 기록의 시각화에 집중합니다.

---

## 2. 주요 작업 단계 및 워크플로우

### Phase 1: 실시간 명령어 방화벽 (Interactive Guard)
- **목표**: 블랙리스트 명령어를 단순히 차단하는 것이 아니라, 실행 전 한 번 더 확인(Confirmation)하거나 관리자 승인을 요구함.
- **워크플로우**:
    1. 사용자가 `rm -rf` 등 위험 키워드 입력.
    2. 서버(`handle_terminal_input`)에서 탐지.
    3. 전송을 일시 중단하고 프론트엔드에 `command_warning` 이벤트 발생.
    4. 브라우저에 "정말 실행하시겠습니까? (이유 작성)" 또는 "관리자 승인이 필요합니다" 팝업 표시.
    5. 확인 버튼 클릭 시에만 셸에 명령어 전송.
- **실현 가능성**: **매우 높음**. 기존 Socket.io 로직에 비동기 대기 프로세스만 추가하면 됨.

### Phase 2: 터미널 세션 녹화 및 리플레이 (Session Snapshot)
- **목표**: 텍스트 로그만으로는 부족한 작업 맥락을 동영상처럼 복기.
- **워크플로우**:
    1. SSH 세션 시작 시 전용 로그 파일(`.cast` 또는 `json`) 생성.
    2. 서버로 들어오는 모든 `terminal_output` 데이터를 타임스탬프와 함께 기록.
    3. 세션 종료 시 로그 파일 저장 및 히스토리 DB와 매핑.
    4. 관리자 페이지에서 '재생(Play)' 버튼 클릭 시 전용 플레이어(`asciinema-player` 등)로 복기.
- **실현 가능성**: **높음**. 저장 공간 관리가 중요하므로 압축 및 주기적인 아카이빙 전략 필요.

### Phase 3: 클러스터 일괄 제어 (Cluster Execution)
- **목표**: 수십 대의 서버에 패치나 점검 명령을 동시에 실행.
- **워크플로우**:
    1. '일괄 제어' 메뉴 진입.
    2. 접속할 호스트들을 다중 선택 (Checkbox).
    3. 통합 터미널/입력창에 명령어 입력.
    4. 백엔드에서 병렬(Parallel)로 SSH 연결 및 실행.
    5. 결과를 호스트별 탭 또는 아코디언 메뉴로 취합하여 시각화.
- **실현 가능성**: **보통**. 다수의 SSH 세션을 동시에 안정적으로 유지하는 리소스 관리 최적화가 핵심.

### Phase 4: 일시 권한 승인 (Just-In-Time Access)
- **목표**: 상시 접속 권한을 없애고 필요할 때만 문을 열어줌 (Zero Trust).
- **워크플로우**:
    1. 사용자가 특정 서버에 대해 "2시간 접속 요청" 생성.
    2. 관리자 대시보드 또는 텔레그램/메시지로 알림 전송.
    3. 관리자가 승인 시 해당 사용자의 세션 토큰에 2시간 타이머 부여.
    4. 2시간 경과 시 서버에서 자동으로 SSH 세션 강제 종료 및 접근 차단.
- **실현 가능성**: **보통**. 타이머 관리 및 스케줄러(Redis/Celery 등) 도입 시 안정성 향상.

## 3. 우선순위 및 버그 방지 전략 (Roadmap Recommendation)

1.  **1순위: Phase 1 (명령어 가드)**
    - **이유**: 기존 로직에 가장 가깝고, 즉각적인 보안 효과가 큼.
    - **전략**: `terminal_input` 버퍼링 로직을 정교화하여 오탐(False Positive)을 줄이는 것이 관건.

2.  **2순위: Phase 2 (세션 녹화)**
    - **이유**: 대규모 인프라 관리 시 사고 조사를 위해 필수적임.
    - **전략**: 파일 IO가 잦으므로 비동기식 쓰기(Async Write)를 적용하여 터미널 응답 속도 저하를 방지.

3.  **3순위: Phase 3 (일괄 제어)**
    - **이유**: 사용자 경험 혁신.
    - **전략**: `SSHManager`를 싱글톤이 아닌 풀링(Pooling) 방식으로 고도화한 후 진행.

4.  **4순위: Phase 4 (JIT)**
    - **이유**: 복잡도가 높고 다른 신뢰 시스템과의 연동이 필요할 수 있음.

---

## 4. 향후 1주일 개발 워크플로우 제안

1.  **월/화**: `Phase 1` 구현 (UI 모달 추가 및 백엔드 인터럽트 제어).
2.  **수/목**: `Phase 2` 기반 마련 (바이너리 출력 로그 저장 및 asciinema 포맷 테스트).
3.  **금/토**: `Phase 3` 프로토타입 (멀티 호스트 선택 및 간단한 명령어 일괄 전송 테스트).

이 계획은 현재의 Flask/Socket.io 아키텍처에서 충분히 실현 가능하며, 특히 **보안 감사 기능**에 집중할 때 프로젝트의 전문성이 가장 돋보일 것입니다.
